# ES 与 ClickHouse 日志采集分析：使用架构与优先级

> 整理日期：2026-08-21
> 适用背景：游戏服（gs）日志已走 `tlog` → ELK（Kibana 平台）；BI 埋点走 ThinkingData 写文件；暂无 ClickHouse。
> 目的：明确 **Elasticsearch（ES）** 与 **ClickHouse（CH）** 各自承担什么角色、哪些场景优先用谁、如何共存。

---

## 1. 一句话结论

| 引擎 | 定位 | 一句话 |
|---|---|---|
| **Elasticsearch** | 排障检索器 | **能搜**：全文、模糊、任意字段下钻、看上下文 |
| **ClickHouse** | 统计分析仓库 | **能算**：聚合、统计、压缩、喂 AI 特征 |

> 两者不是替代关系，而是**分工关系**。日志场景的最佳实践是同一份数据分别进两套：CH 做统计底座，ES 做排障检索。

---

## 2. 能力对比总表

| 维度 | ClickHouse | Elasticsearch | 结论 |
|---|---|---|---|
| 写入吞吐 | 极高（列式顺序写，Kafka 直写 50-200MB/s） | 较高但低 5-10 倍（倒排索引 + segment merge 开销） | **CH** |
| 数据压缩 | 列式 + LZ4/ZSTD，10-20 倍 | 压缩率低，索引额外占空间 | **CH**（占地约 ES 1/3-1/5） |
| 聚合/统计 | 极强（GROUP BY 百万行秒级，物化视图预聚合） | 一般（doc_values 聚合，量大变慢） | **CH 碾压** |
| 全文搜索 | 弱（无倒排，like 全表扫） | 极强（倒排索引、分词、高亮、相关性） | **ES 碾压** |
| 精确过滤 | 强（主键/分区裁剪极快） | 中 | **CH** |
| 点查（按 ID 取单条） | 快 | 快 | 平 |
| 写入实时性 | 即写即查 | 默认 1s refresh 延迟 | **CH** |
| 单条更新/乱序 | 弱（主键模型不擅长单行 update） | 强（文档级更新） | **ES** |
| 运维复杂度 | 低（单进程、无额外依赖） | 高（集群、分片、堆调优、脑裂、GC） | **CH** |
| 可视化 | 一般（Grafana 强，无 Kibana） | 极强（Kibana：Discover/Alert/ML/SIEM） | **ES** |
| SQL | 完整 SQL | DSL 为主，SQL 阉割版 | **CH** |
| 生态成熟度 | 后起，社区活跃 | 非常成熟 | **ES** |

## 3. 使用优先级（按场景）

### 🥇 第一优先 — 明确用 ClickHouse

| 场景 | 原因 | 例（游戏服） |
|---|---|---|
| **聚合统计 / 报表** | 聚合性能碾压 ES | 按渠道算日活/付费/LTV、错误率分布、P99 延迟 |
| **长期明细存档** | 压缩率高，存 30 天以上成本低 | 埋点行为明细、渠道 ROI 明细 |
| **AI 特征底座** | 物化视图实时维护滑窗特征，供模型在线/离线消费 | 玩家付费频次、活跃滑窗、渠道质量特征 |
| **时序指标监控** | 高吞吐写入 + 长时间序列聚合 | 接口 QPS、GC、在线人数时序，配 Grafana |
| **实时异常检测输入** | 高基数 × 高吞吐聚合 | 反作弊（同设备多账号）、告警阈值计算 |

### 🥈 第二优先 — 明确用 Elasticsearch

| 场景 | 原因 | 例（游戏服） |
|---|---|---|
| **故障排障** | 全文搜单条日志、看上下文、任意字段下钻 | "搜 5 分钟前某个 panic 附近发生了什么" |
| **错误聚合定位** | 按 message/堆栈聚合去重、关联 requestId | 线上报错按错误信息归类、按玩家/订单串联 |
| **Kibana 可视化排障** | Discover/Alert 生态无可替代 | 现网告警、慢查询分析、SIEM 安全 |
| **文档型数据查询** | 结构多变、需要全文 | 玩家反馈、运营备注、任意 JSON 日志 |

### 🥉 第三优先 — 按成本/现状权衡

| 场景 | 建议 | 说明 |
|---|---|---|
| **小规模全量日志** | 先用 ES | 数据量小（< 500GB）时 CH 聚合优势不明显，ES 一套省心 |
| **短周期排障 + 长周期统计** | 双写 | 排障进 ES（保留 7-30 天），统计进 CH（长期） |
| **已有 ELK 且能用** | 别急着换 | 只有出现"聚合慢/存储贵/写入瓶颈"再引入 CH |

## 4. 双引擎共存的推荐架构

```
游戏服 tlog / BI 埋点
        │
        ▼
      Kafka（统一缓冲）
        ├─────────────────► Filebeat/Logstash → Elasticsearch → Kibana（排障检索，TTL 7-30天）
        └─────────────────► ClickHouse 写入端（统计仓库，长期保留）
                                  │
                                  ├─ 明细表（MergeTree，按天分区）
                                  ├─ 物化视图聚合表（AggregatingMergeTree，实时特征）
                                  └─ 定时任务 → 报表 / AI 特征输出
```

### 各环节职责

| 组件 | 职责 |
|---|---|
| Kafka | 削峰缓冲、解耦，两边都能独立消费 |
| Elasticsearch | 排障检索、全文搜索、Kibana 告警（短周期保留） |
| ClickHouse | 聚合统计、长期存档、AI 特征、报表（长期保留） |
| Grafana | CH 指标的可视化（补 Kibana 不接 CH 的缺口） |

## 5. 结合当前项目的落地建议

### 现状盘点
- 日志：`tlog` → ELK（Kibana），**适合排障，聚合/长期统计是短板**
- 埋点：`game/bi` → ThinkingData 写文件，走的是 TA 自己的采集链路
- 无 ClickHouse，无 Kafka 统一日志通道（需要确认现有采集是否已过 Kafka）

### 优先级建议
1. **先解决"聚合算不动"**：如果现有 ELK 上按渠道/按日的聚合报表开始变慢或磁盘吃紧 → 引入 ClickHouse 做统计仓库
2. **渠道质量分析优先**：正在做的渠道对接（咸鱼 mohe_xy 等）天然需要"按渠道聚合 ROI/LTV/留存"，这是 CH 最直接的落地场景
3. **AI 特征其次**：等 CH 稳定后，把埋点/行为特征物化视图建起来喂给付费预测、流失预警
4. **不动的部分**：排障日志继续留在 ES，不迁移；Kibana 继续用

### 渐进路线
```
Phase 1：Kafka 双写（ES 排障 + CH 统计），建渠道 ROI 聚合表
Phase 2：加物化视图实时特征（玩家活跃/付费滑窗）
Phase 3：接入 AI 模型特征消费 + Grafana 指标可视化
```

## 6. 避坑要点

| 坑 | 说明 |
|---|---|
| 别用 CH 做全文搜索 | like 全表扫会拖垮集群，排障场景留在 ES |
| 别用 ES 做超大规模聚合 | 内存吃紧、慢，报表/统计场景交给 CH |
| CH 单行更新弱 | 日志是追加型（MergeTree）没问题，但别拿它存"频繁改状态的业务数据" |
| 双写成本 | 写两遍 + 两套存储，但 CH 压缩省回来的通常大于 ES 单套 |
| 表结构 | CH 要求相对固定，字段规划好再上线；ES 结构灵活 |

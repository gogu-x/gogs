# 多人协同Boss战斗会话设计文档

## 1. 设计目标

- N个玩家可以在不同时间点，随时加入或退出同一个Boss的战斗
- Boss技能同时支持单体目标（点名/嘲讽/最高威胁值）和群体目标（AOE/全体嘲讽）
- 保证Boss状态（血量、buff）在多人并发攻击的情况下始终一致，且不依赖锁
- 支持基于伤害贡献的死亡结算和奖励分配

---

## 2. 架构模型：Boss协程 + 事件驱动

### 2.1 核心原则

**谁的状态，就由谁的协程处理。** 不使用共享内存+锁，也不使用"tick循环里集中遍历所有人再统一读写"的模型，而是让每个战斗参与者（Boss、每个玩家的部队）各自拥有一个独立运行的协程，状态完全私有，协程之间只通过事件（消息）通信：

```
Boss协程 { 私有状态: 血量、buff、技能CD、DamageRecord、Combatants表 }
玩家A协程 { 私有状态: A的部队血量、A的技能CD、A的buff }
玩家B协程 { 私有状态: B的部队血量、B的技能CD、B的buff }
```

任何一方要修改另一方的状态，不能直接读写对方的内存，只能**发事件**给对方，由对方自己的协程收到事件后修改自己的状态：

```
A要攻击Boss:       A协程 --攻击事件--> Boss协程 (由Boss协程扣自己的血、改自己的DamageRecord)
Boss技能命中A:      Boss协程 --伤害事件--> A协程 (由A协程扣自己部队的血)
Boss技能命中所有人:  Boss协程 --伤害事件--> A协程
                              --伤害事件--> B协程
                              --伤害事件--> C协程   (群体技能=向多个目标各发一份事件，不是Boss直接改多个人的状态)
```

### 2.2 为什么这样天然没有竞争问题

- Boss协程内部只有它自己在收发消息、修改自己的血量/DamageRecord，即使A、B、C同时发"攻击事件"过来，这些事件在Go里通过channel投递，**Boss协程从channel里逐个取出处理**，本质上还是排队串行，只是排队的机制从"tick循环里for遍历"换成了"从channel里阻塞式取事件"——两者都是排队，只是实现方式不同，但都保证了同一时刻只有一个事件在修改Boss的状态。
- A协程只修改A自己的状态，不会有其他协程同时去改A的血量，所以A协程内部也不需要加锁。
- 没有任何一段代码是"A协程直接写Boss的DamageRecord"或者"Boss协程直接改A的部队血量"——这条边界必须严格遵守，一旦有协程跨界直接修改别人的状态，就退化成了共享内存并发写入的老问题（伪装成协程，但没有解决根本问题）。

### 2.3 与旧方案(tick集中遍历)的区别

| 维度 | 旧方案(tick集中遍历共享状态) | 新方案(Boss协程+事件驱动) |
|---|---|---|
| 状态存放 | 一个共享的BattleSession结构体，所有人的数据都在里面 | 每个参与者的状态私有在自己的协程里，互不可见 |
| 驱动方式 | 外部定时器驱动，每个tick统一遍历所有人计算一遍 | 事件驱动，谁发生了行动(攻击/技能触发)才产生事件，没有固定周期的"全量遍历" |
| 排队机制 | 一个大循环里for遍历所有Combatant | 每个协程自己的事件channel，各自独立排队 |
| 新玩家加入 | 需要等到下一个tick边界统一生效，否则遍历中修改map不安全 | 直接发一条"加入"事件给Boss协程即可，Boss协程在处理完当前事件后自然会处理这条加入事件，天然排在队列里，不需要专门等"tick边界" |
| 群体技能实现 | 遍历Combatants表，直接改每个人的血量字段 | Boss协程遍历自己持有的目标列表，对每个目标分别发一条伤害事件，各自协程处理 |

**注意**：抛弃了"固定周期检查"这个概念本身吗？不是。CD/攻速判定仍然需要一个时间驱动的触发点（见第4节），但这个触发变成了**每个协程自己内部的一个定时器**，用来驱动"检查自己的技能CD是否到了、该不该主动出手"，而不是一个外部的、集中遍历所有人的调度循环。这是本质区别：旧模型的驱动是"外部的、全局的调度者"，新模型里每个协程管理自己的时间驱动，互不依赖。

## 3. 核心数据结构（按协程归属拆分）

### 3.1 Boss协程持有的状态

```
BossActor {
    BossID           int64
    State            SessionState                // 未开始/进行中/已结束
    CurrentHp        int64
    MaxHp            int64
    BuffList         []*BuffInstance
    Actions          []*ActionSource             // Boss自己的普攻/技能行动源(见第4节)
    CurrentTarget    int64                       // 当前单体锁定目标(玩家ID)
    Phase            int32                       // 战斗阶段
    Combatants       map[int64]*CombatantRef      // 当前参战者列表(只存引用信息，不存对方的血量等私有状态)
    DamageRecord     map[int64]int64             // 伤害贡献表(玩家ID -> 累计伤害)，只有Boss协程能修改
    InboxChan        chan BattleEvent             // 事件收件箱，所有对Boss的操作都通过这个channel投递
}

CombatantRef {
    PlayerID       int64
    OutboxChan     chan BattleEvent    // 发往该玩家协程的事件发送通道(Boss发伤害事件走这里)
    ThreatValue    int64               // 威胁值(Boss用来做单体目标选择，属于Boss侧维护的数据)
    JoinTs         int64
    IsAlive        bool                // Boss侧记录的"这个人是否还活着"(由玩家协程上报状态变化事件同步过来)
}
```

**关键设计**：`Combatants` 里存的不是玩家部队的完整血量/状态（那属于玩家协程私有），只存**Boss协程做决策需要的最小信息**（威胁值、是否存活、往哪个channel发事件）。玩家部队真实的血量细节，Boss协程不直接持有，也不需要持有。

### 3.2 玩家协程持有的状态

```
CombatantActor {
    PlayerID         int64
    TroopSnapshot    *TroopSnapshot        // 加入时的阵容快照
    CurrentHp        int64                 // 部队当前血量(只有该玩家协程自己能改)
    BuffList         []*BuffInstance       // 身上的buff/debuff
    Actions          []*ActionSource       // 自己的普攻/技能/宝物行动源
    IsAlive          bool
    BossOutbox       chan BattleEvent       // 发往Boss协程的事件发送通道(自己发起攻击走这里)
    InboxChan        chan BattleEvent       // 事件收件箱(接收Boss发来的伤害/debuff事件)
}
```

### 3.3 事件定义

```
BattleEvent {
    EventType     EventType    // 攻击 | 受到伤害 | 加入 | 退出 | 死亡 | Buff施加 | 心跳/CD检查
    FromID        int64        // 事件发起者
    ToID          int64        // 事件目标
    Timestamp     int64
    Payload       interface{}  // 具体数据(伤害值、buff信息、加入请求的阵容快照等)
}
```

## 4. 行动触发与CD判定：谁的行动，谁的协程自己驱动

之前的方案里，"检查CD是否到期"是外部循环遍历所有人的Actions字段来判定的。现在这个职责下放给每个协程自己：

```
每个协程(Boss协程 / 每个CombatantActor)内部各自运行一个独立的自驱动循环:

for {
    select {
    case event := <-自己的InboxChan:
        处理收到的事件(见4.1)

    case <-自己的行动检查定时器.C:     // 每个协程自己的定时器，检查自己的Actions是否有就绪的
        遍历自己的Actions:
            if now >= action.NextReadyTs:
                执行这个行动(见4.2)
                action.NextReadyTs = now + action.IntervalMs
    }
}
```

这是Go语言`select`语句的典型用法：**一个协程要同时处理"别人发来的事件"和"自己内部的定时触发"，用select监听多个channel（其中一个是time.Ticker的channel）**，两类事件都进入同一个处理循环，天然顺序处理，不会出现"处理事件的同时又在检查CD"的并发冲突——因为它们本来就是同一个for循环里顺序执行的两个分支，不是两个并行的协程。

### 4.1 收到事件时的处理（以Boss协程收到"攻击事件"为例）

```
Boss协程收到 BattleEvent{EventType: 攻击, FromID: A, Payload: A的本次攻击信息}:
    1. 检查Boss.State是否已经"已结束" → 是则直接忽略这个事件(战斗已经结束，迟到的攻击事件无效)
    2. 检查A是否还在Combatants表里(是否已经退出) → 不在则忽略
    3. 调用伤害计算(纯函数，输入A的攻击信息+Boss当前状态，输出伤害值)
    4. Boss.CurrentHp -= 伤害值，clamp到0
    5. Boss.DamageRecord[A] += 伤害值(原始伤害记账)
    6. Boss.Combatants[A].ThreatValue += 伤害值
    7. 判断 CurrentHp <= 0？
        是 → 触发死亡结算流程(见第6节)，之后不再处理任何后续事件(或只处理退出类事件用于清理)
        否 → 结束本次处理，回到for循环等待下一个事件/定时器触发
```

### 4.2 自己的定时器触发时的处理（以Boss协程的技能CD就绪为例）

```
Boss协程定时器触发，发现某个技能Action.NextReadyTs已到:
    1. 判断该技能是单体还是群体(TargetType)
    2. 单体: 从Combatants表里按威胁值/规则选出CurrentTarget
       群体: 目标 = Combatants表里所有存活的CombatantRef
    3. 对每个目标:
        计算Boss这个技能对该目标的伤害/效果(纯函数)
        通过 目标.OutboxChan 发送一条"受到伤害"事件给该目标的协程
        (Boss协程发完事件就结束，不等待、不关心对方怎么处理，
         对方部队的血量变化由对方协程自己处理，Boss协程不直接改)
    4. 重新排期该Action的NextReadyTs
```

**这一步体现了群体技能在新架构下的实现方式**：不是"Boss直接遍历Combatants给每个人的血量字段做减法"，而是"Boss决定好目标列表后，给每个目标各发一条独立的事件，剩下的由各自的协程自己处理"。这样Boss协程完全不触碰任何玩家的私有状态，边界清晰。

### 4.3 出手权互斥规则（技能/宝物优先于普攻）在新模型下的实现

这条规则是"同一个协程自己的多个Actions之间"的调度问题，不涉及跨协程通信，处理方式不变：

```
每个协程自己的定时器触发时:
    1. 先检查自己的Actions里，是否有 技能/宝物 类型的已就绪(NextReadyTs已到)
    2. 若有 → 只处理这些技能/宝物(按Priority排序执行)，本轮不处理普攻(普攻的NextReadyTs不变，不重新排期)
    3. 若没有技能/宝物就绪，只有普攻就绪 → 处理普攻
```

因为Actions是这个协程自己私有的数据，这部分逻辑完全在协程内部完成，不需要考虑并发问题，和之前的设计一致，只是执行的载体从"外部循环里的一个分支"变成了"协程自己的定时器回调"。

## 5. 生命周期管理

### 5.1 会话创建

```
Boss进入"可被攻击"状态时:
    1. 启动一个新的BossActor协程，初始化State=进行中、满血、无buff
    2. 该协程立即进入自己的事件循环(第4节的select for循环)，开始监听InboxChan和自己的定时器
```

### 5.2 玩家加入（随时可加入，不需要等待"批次边界"）

```
玩家发起加入请求
    │
    ▼
前置校验(在接收请求的地方立即执行，不需要进Boss协程):
    - 玩家资格(战力/等级)
    │ 校验通过
    ▼
创建该玩家的CombatantActor协程，初始化TroopSnapshot、Actions
    │
    ▼
向Boss协程的InboxChan发送一条"加入"事件 { FromID: 玩家ID, Payload: OutboxChan引用等 }
    │
    ▼ (Boss协程在自己的事件循环里，处理完当前正在处理的事件后，自然会取到这条加入事件)
Boss协程处理"加入"事件:
    Combatants[玩家ID] = &CombatantRef{ ... }
    (完成，玩家的普攻/技能行动从这一刻起就会被自己的协程独立驱动)
```

**这里不再需要"待处理队列+等待批次边界"这套机制**：因为Boss协程处理事件本身就是逐个从channel取出串行处理的，新来的"加入事件"和"攻击事件"一样，都是排在队列里等着被处理，不存在"遍历过程中map被并发修改"的问题（因为根本没有"遍历所有人"这个动作，Boss协程要处理谁，就是从channel里拿到的这一个事件）。

### 5.3 玩家退出

```
主动退出: 玩家协程向Boss协程InboxChan发送"退出"事件 → Boss协程收到后从Combatants表删除该条目
被动退出(部队阵亡): 玩家协程自己判断到CurrentHp<=0后，自己发送"退出"事件给Boss协程，然后自己的协程可以退出/归档
被动退出(掉线/挂机): 由外部监控(比如一个独立的巡检协程)检测到超时后，代替该玩家发送"退出"事件给Boss协程
```

### 5.4 会话结束

```
结束条件(任一触发，均由Boss协程自己在事件处理循环中判断):
    - CurrentHp<=0                     → 死亡结算(见第6节)
    - Combatants为空且持续超过X秒        → 超时结束
    - 达到战斗时长上限                   → 强制结束

结束后动作:
    State = 已结束
    向所有还在Combatants表里的玩家的OutboxChan发送"战斗结束"事件
    Boss协程退出自己的for循环，协程自然结束(Go协程没有显式销毁，函数返回后由GC回收)
```

## 6. 死亡结算流程

死亡判定和死亡结算全部在Boss协程内部完成，不需要跨协程同步：

```
Boss协程在处理某个事件/定时器触发后，发现CurrentHp<=0:
        │
        ▼
1. State = 已结束(死亡)，之后收到的攻击类事件直接忽略(见4.1第1步)
        │
        ▼
2. 遍历自己的DamageRecord，计算TotalDamage = Σ(所有伤害值)
        │
        ▼
3. 逐个计算每个参与者的奖励占比 = 该玩家伤害 / TotalDamage
   (可选)额外给最后一击者击杀奖励
        │
        ▼
4. 生成击杀汇总战报
        │
        ▼
5. 遍历Combatants，向每个人的OutboxChan发送"死亡结算结果"事件
   (各玩家协程收到后，自己处理奖励发放/展示，Boss协程不直接操作玩家的数据)
        │
        ▼
6. Boss协程退出事件循环，整个BossActor协程结束
```

## 7. 并发与一致性保证（新模型下的说明）

| 保证点 | 实现方式 |
|---|---|
| Boss状态只被一处修改 | Boss的所有状态(血量/DamageRecord/Combatants)只在BossActor协程内部被修改，其他协程只能通过发事件请求修改，不能直接访问 |
| 玩家状态只被一处修改 | 同理，玩家部队的血量等状态只在其CombatantActor协程内部修改 |
| 事件处理天然串行 | 每个协程的事件循环是单个for+select，同一时刻只处理一个事件或一次定时器触发，不需要锁 |
| 死亡判定只触发一次 | 判定和结算都在Boss协程同一次事件处理内完成，判定后立即转换State，后续事件在第一步就被过滤 |
| 阵容中途变化不影响本场战斗 | CombatantActor在创建时做一次TroopSnapshot，协程生命周期内使用这份快照 |
| 群体技能不产生竞争 | Boss协程决定目标列表后，对每个目标各发一条独立事件，不直接改多个玩家的状态；各玩家协程各自独立处理收到的事件 |

---

## 8. 需要额外确认的策划参数

- Boss/玩家协程内部定时器的检查间隔：多久检查一次自己的Actions是否有就绪的(直接影响CD判定精度和CPU开销)
- 参战人数上限：Boss协程的Combatants表最多允许多少条目
- 掉线/挂机踢出阈值：多久没有有效行动会被巡检协程判定为"挂机"并发送退出事件
- 战斗最大时长：超时未击杀是否强制结束
- 单体嘲讽目标切换规则：威胁值最高/随机/固定优先级等策略选择
- 群体技能命中人数上限：AOE技能最多同时命中多少人
- 新加入玩家的初始行动状态：加入那一刻，普攻/技能是否立即可用
- 普攻"饿死"保底机制：技能/宝物持续抢占出手权时，是否需要保证普攻最终能获得出手机会

---

## 9. 落地实现要点（Go语言层面）

- Boss协程和每个玩家协程都是标准的Go goroutine，用`chan BattleEvent`做channel通信
- 每个协程的主循环用`select`同时监听事件channel和`time.Ticker`
- **严禁**任何协程直接持有并修改另一个协程的结构体指针字段——所有跨协程的状态变更都必须通过发送事件完成，这是保证无锁并发安全的唯一前提，代码review时需要重点检查这条边界是否被破坏
- Boss协程结束后（战斗结束），需要显式关闭或不再使用对应的channel，避免其他协程往一个没有接收者的channel发消息导致阻塞（如果channel是无缓冲的）；建议InboxChan使用一定长度的有缓冲channel，避免发送方因接收方处理慢而阻塞

## 10. 通用化：CombatActor 协议

前面几节里的"Boss协程"和"玩家协程"，本质上是同一种东西的两个具体实例——都是"一个拥有血量、行动源、能收发战斗事件的独立协程"。为了让Boss战、普通怪物战、PVP都能复用同一套协程调度框架，而不是每种场景各写一套，需要把公共部分抽象成一个通用协议。

### 10.1 抽象出的公共协议

任何参与战斗的实体（Boss、玩家部队、普通怪物、PVP对手）都实现同一个接口/协议，暂称为 `CombatActor`：

```
CombatActor 接口 {
    GetID() int64
    GetInbox() chan BattleEvent          // 事件收件箱，供其他Actor发事件过来
    IsAlive() bool

    // 由具体类型实现的差异化行为:
    OnReceiveEvent(event BattleEvent)     // 收到事件时如何处理(攻击/伤害/加入/退出等)
    OnActionReady(action *ActionSource)   // 自己的某个行动(普攻/技能)CD到了时如何处理
    OnDeath()                             // 血量归零时如何结算(死亡结算逻辑因场景而异)
}
```

**通用的驱动循环**（不因Boss/玩家/怪物而变化，写一次，所有类型共用）：

```
func RunActorLoop(actor CombatActor) {
    ticker := time.NewTicker(检查间隔)
    defer ticker.Stop()
    for {
        select {
        case event := <-actor.GetInbox():
            if !actor.IsAlive() {
                continue  // 已死亡的Actor不再处理任何事件(除了必要的清理类事件)
            }
            actor.OnReceiveEvent(event)

        case <-ticker.C:
            if !actor.IsAlive() {
                return  // 已死亡，退出循环，协程结束
            }
            for _, action := range actor.GetActions() {
                if now >= action.NextReadyTs {
                    actor.OnActionReady(action)
                }
            }
        }
    }
}
```

这个循环函数是**唯一的、通用的调度框架**，不管是启动一个Boss、一个玩家部队还是一个PVP对手，都是调用同一个`RunActorLoop(具体的actor实例)`，差异只体现在每种类型各自实现的`OnReceiveEvent`/`OnActionReady`/`OnDeath`里。

### 10.2 各场景下的具体实现差异

| 场景 | 实现类型 | OnReceiveEvent的差异 | OnDeath的差异 |
|---|---|---|---|
| Boss战(多人) | BossActor | 收到攻击事件→扣自己血、记录DamageRecord(伤害贡献表) | 按DamageRecord占比分配奖励给所有参战者 |
| Boss战(玩家部队) | CombatantActor | 收到伤害事件→扣自己部队血、检查是否需要发退出事件给Boss | 通知自己退出Boss战，个人战斗结算(自己这次的表现战报) |
| 单人Boss(1v1) | 同上两种类型，Combatants表只有一条记录，但需要额外接入10.5节的仲裁机制 | 逻辑基本不变 | 不是简单的"占比恒为100%"，因为玩家死亡会直接终止战斗产生互斥结局，需按10.6节的方式判定胜负 |
| PVP(玩家对玩家) | PvpActor | 收到攻击事件→扣自己血、判断胜负(零和逻辑，不是伤害贡献表) | 通知对方"你赢了/你输了"，按胜负结算奖励/惩罚，不走占比分配 |
| 普通怪物(非Boss小怪) | MonsterActor | 逻辑可以更简单(比如没有技能，只有普攻)，或者复用BossActor但去掉阶段/群体技能部分 | 死亡后简单掉落，不需要复杂的多人分配逻辑 |

### 10.3 这样抽象带来的好处

- **调度框架只写一次**：`RunActorLoop`、事件channel的收发机制、"谁的状态归谁改"这条底层原则，在所有场景下完全复用，不需要给PVP、Boss战、怪物战分别写三套并发处理代码。
- **新增战斗类型的成本降低**：以后如果要做新的玩法（比如三方混战、援护/协战机制），只需要新写一个实现了`CombatActor`接口的类型，接入已有的`RunActorLoop`，不需要重新设计并发模型。
- **并发安全性保证是统一的、可复用的**：因为所有类型都遵循"只通过事件通信，不直接跨协程改状态"这一条硬性约束，review代码时只需要检查每种`OnReceiveEvent`/`OnActionReady`的实现是否遵守了这条边界，而不需要对每种战斗类型单独分析并发正确性。

### 10.4 PVP场景需要额外注意的规则问题（非架构问题，是业务规则问题）

- **双方几乎同时把对方打死，如何判定胜负**：架构层面双方协程各自独立处理"收到攻击"事件，不存在竞争，但业务上需要显式定义"双方同一时刻致死对方"算平局、算双输，还是按事件到达的先后顺序判定（谁先扣死对方谁赢）。
- **PVP不需要"随时加入"机制**：PVP通常是1v1或固定人数的对战，不像Boss战需要处理"战斗进行中还能有新人加入"这种情况，所以PVP场景下`CombatActor`可以不实现"加入"相关的事件处理，这是允许的——接口方法可以按需实现，不需要每种类型都用到全部事件类型。

### 10.5 PVP胜负判定的落地方案：主协程回调仲裁

"谁先死亡判负"这条规则在两个独立协程各自并行判断自己是否死亡的情况下，本身是没有意义的比较——A协程和B协程各自的"死亡时刻"只在各自协程的本地时间线上成立，不存在一个天然的、全局的先后顺序。要让"谁先死"有唯一确定的答案，必须引入一个**单一的仲裁点**，所有死亡判定都汇聚到这一个点上按到达顺序决定胜负。

这个仲裁点不需要专门新起一个协程，可以直接复用**创建这场PVP战斗时所在的主协程**，让它同时承担"战斗生命周期管理"和"胜负仲裁"两个职责：

```
创建PVP战斗时，在主协程里:
    注册一个死亡结算回调: OnBattleEnd(winnerID, loserID)
    创建一个共享的死亡事件channel: deathEventChan := make(chan DeathEvent, 2)
    结果已判定 := false   // 只被主协程读写，不需要加锁

    启动A、B两个CombatActor协程，把 deathEventChan 的发送端传给它们

主协程自己的事件循环:
    for {
        select {
        case death := <-deathEventChan:
            if 结果已判定 {
                continue   // 已经判过胜负了，忽略后续到达的死亡事件(处理"双方几乎同时死"的情况)
            }
            结果已判定 = true
            winnerID, loserID := 根据death确定胜负(死者输，另一方赢)
            OnBattleEnd(winnerID, loserID)   // 回调在主协程里执行，天然安全，不需要锁
            return   // 战斗结束，主协程可以退出
        }
    }

A协程判断自己CurrentHp<=0:
    不直接下结论"我输了"，而是: deathEventChan <- DeathEvent{LoserID: A的ID, Timestamp: now}
    发送完毕，A协程自己的职责结束(可以继续处理清理逻辑或直接退出循环)

B协程判断自己CurrentHp<=0:
    同理: deathEventChan <- DeathEvent{LoserID: B的ID, Timestamp: now}
```

**这个方案为什么能解决"谁先死"的判定问题**：

- `结果已判定` 这个布尔状态只被主协程自己读写，因为只有一个协程会碰它，不需要锁——这也是"死亡结算回调必须在主协程里执行"这条约束真正要解决的问题：把一个需要"仅此一次、且结果确定"的操作，限定在唯一一个执行上下文里完成。
- `deathEventChan` 是唯一的仲裁点：即使A协程和B协程几乎同一时刻各自判断自己死了，两条`DeathEvent`消息通过Go的channel机制，必然有一条先被主协程的`select`取出——**channel本身的发送/接收语义保证了多个发送者投递到同一个channel时，接收方能确定性地逐个取出**，这就是"谁先谁后"唯一确定的来源，不需要比较任何时间戳。
- 第二条到达的死亡事件被`结果已判定`挡住直接忽略，天然处理了"双方互相同归于尽"的场景——按谁的死亡事件先被主协程取到判谁输，规则确定，不会出现两边都判赢或者都判输的矛盾结果。

**这与之前提到的"引入裁判协程"是同一个思路的不同实现**：不需要专门新起一个协程去做裁判，而是让创建这场战斗时已经存在的主协程，顺带承担"胜负仲裁"这个职责——只要保证死亡判定和回调调用被限定在唯一确定的一个执行上下文里完成，用哪个协程承担这个角色都可以，复用主协程是更自然、更节省资源的选择。

**适用边界**：这个方案解决的是"实时制PVP"（双方各自独立跑攻速/CD，可能在任意时刻致死对方）下"谁先死"的判定问题。如果PVP是回合制（双方按固定顺序轮流出手），"谁先死"由回合结算顺序天然唯一确定，不需要这套死亡事件仲裁机制，直接在回合结算流程里判断即可(参见10.4之前的讨论)。

## 11. 最终结算流程（统一方案）

前面几节分别讨论了"多人打Boss"、"1v1打Boss"、"PVP"三种场景，看起来像是三套不同的机制，但实际上可以用同一个判断标准统一起来，本节给出最终的、可直接落地的完整结算流程。

### 11.1 唯一的判断标准：死亡结果是否互斥地终止整场战斗

不按"这是PVE还是PVP"分类，只问一个问题：**这个战斗里，任意一方死亡，是否会立即终止整场战斗、且和另一方的死亡构成互斥的最终结局（不可能双方都算赢，也不可能"部分胜利"）**？

```
是 → 归为"互斥终局"类型，必须用11.3节的仲裁机制来确定"谁先死"
否 → 归为"独立退出"类型，各方死亡各自处理，不需要仲裁，直接用第6节的死亡结算流程
```

按这个标准重新分类：

| 场景 | 归类 | 原因 |
|---|---|---|
| 多人打Boss(N个玩家, N≥2) | 独立退出 | 某个玩家死亡只是他自己退出，不影响其他人继续打，也不影响"Boss最终是否被击杀"这个结局 |
| 1v1打Boss(1个玩家) | 互斥终局 | 玩家死→战斗立即结束(讨伐失败)；Boss死→战斗立即结束(讨伐成功)；二者互斥，必须知道谁先死 |
| PVP(玩家对玩家) | 互斥终局 | 任一方死亡直接终止战斗，产生唯一的胜负结局 |
| 多个怪物围攻1个玩家 | 独立退出 | 玩家死亡是玩家侧的结局，和"某个怪物是否存活"无关，不构成互斥 |

### 11.2 "独立退出"类型的结算流程（多人Boss战为代表）

```
任意一方(某个玩家 或 Boss)在自己的协程内部判断 CurrentHp<=0:
        │
        ▼
1. 将自己的State置为"已结束"，之后收到的战斗类事件直接忽略
        │
        ▼
2. 判断死者身份:
   若死者是Boss → 走第6节"死亡结算流程"(遍历DamageRecord按占比分配奖励)
   若死者是某个玩家 → 走5.3节"被动退出"流程(通知Boss协程移除该玩家，
                     该玩家自己结算个人战斗表现，不影响Boss战继续进行)
        │
        ▼
3. 结束(不需要跨协程仲裁，因为这个死亡判定不影响另一方的最终结局)
```

### 11.3 "互斥终局"类型的结算流程（1v1打Boss / PVP为代表，统一方案）

```
创建战斗时，在主协程(战斗发起时所在的协程)里完成以下初始化:
        │
        ▼
1. 创建共享死亡事件channel: deathEventChan := make(chan DeathEvent, 2)
   注册结算回调: OnBattleEnd(winnerID, loserID)
   初始化 结果已判定 := false (只被主协程读写，不加锁)
        │
        ▼
2. 启动双方各自的CombatActor协程(1v1场景是"玩家协程"+"Boss协程"；
   PVP场景是"玩家A协程"+"玩家B协程")，把deathEventChan的发送端传给双方
        │
        ▼
3. 主协程进入事件循环，等待死亡事件:
   for {
       select {
       case death := <-deathEventChan:
           if 结果已判定 { continue }   // 忽略后到达的(处理同归于尽的情况)
           结果已判定 = true
           winnerID, loserID := 根据death.LoserID确定胜负
           OnBattleEnd(winnerID, loserID)
           return
       }
   }
        │
        ▼ (与主协程并行运行)
4. 双方各自的协程在判断自己CurrentHp<=0时:
   立即执行: deathEventChan <- DeathEvent{LoserID: 自己的ID, Timestamp: now}
   (要求: 判断死亡到发送事件之间不能夹带耗时逻辑，比如战报生成、掉落计算等
    要放到发送事件之后或OnBattleEnd回调触发之后再做，保证"血量归零"和"事件送达"
    这两个时刻足够接近，"谁的事件先到"才能公平反映"谁真的先死")
        │
        ▼
5. 主协程的OnBattleEnd(winnerID, loserID)回调执行:
   - 若是1v1 Boss战: winnerID是玩家 → 讨伐成功结算(掉落/奖励)
                     winnerID是Boss → 讨伐失败结算(可能有安慰奖/惩罚)
   - 若是PVP: winnerID对应的玩家 → 胜利结算(奖励/掠夺对方资源)
             loserID对应的玩家 → 失败结算(可能有惩罚/资源损失)
        │
        ▼
6. 结算完成，向双方协程发送"战斗结束"通知(如果双方协程还需要做善后处理，
   比如清理自己的状态、退出自己的事件循环)
```

### 11.4 完整决策图：新场景该走哪套流程

```
新的战斗玩法需求
        │
        ▼
┌─────────────────────────────┐
│ 任一方死亡是否会立即终止整场战斗，  │
│ 且与另一方的死亡构成互斥的最终结局？ │
└─────────────────────────────┘
        │
   是 ──┼── 否
   │        │

```

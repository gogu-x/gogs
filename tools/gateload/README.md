# 网关业务压测

通过真实 WebSocket/protobuf 链路创建独立账号，校验注册、登录和装备、魂玉、天赋、活动列表响应的业务码。所有用户通过四类查询后计入在线数，每隔指定间隔轮询一个查询。连接不重试，业务错误或超时退出该玩家，避免重试掩盖失败。

```bash
go build -o /tmp/gateload ./tools/gateload
/tmp/gateload -addr ws://127.0.0.1:8001/ws -server 1 -users 20000 -rate 100 -hold 10m -interval 5s
```

每秒启动 100 个玩家，全部首次流程结束后进入 10 分钟稳态。若部分玩家失败，稳态在线数会低于目标，必须判定未达到目标，不能用累计登录数替代同时在线数。启动时日志记录账号前缀，测试会留下注册账号和角色数据；退出仅关闭连接，不删除数据库记录。

标准输出每 10 秒输出一行 JSON；标准错误记录阶段日志。`ramp/` 和 `hold/` 分别记录升压和稳态响应统计；`errors` 按阶段、请求、错误聚合。分位数仅包含成功响应，需同时查看错误数。直方图按毫秒向下取整，0 表示小于 1 毫秒，60001 桶为上限溢出桶。请求延迟从编码前开始直到解码并确认响应业务码，包含客户端及网络开销。

每个连接只有一个在途请求，等待预期类型响应时忽略其他类型的推送，超时时关闭连接。在线计数表示已通过注册、登录及首轮全部查询且尚未观察到失败的客户端；断线可能到下次查询才被观测，最长为查询间隔加请求超时。本工具没有独立服务端在线数校验。持续成功响应能够验证连接仍可访问玩家服务。

默认每人每 5 秒请求一次，2 万在线目标约 4000 请求/秒，四个查询各约 1000 请求/秒。此场景不覆盖战斗、聊天广播、消耗/奖励等写操作，也不覆盖突发 2 万人瞬时登录、重连或长时间稳定性。压测机与服务端同机时，回环网络延迟及共享 CPU/内存会影响结果，不能替代真实公网体验测试。
